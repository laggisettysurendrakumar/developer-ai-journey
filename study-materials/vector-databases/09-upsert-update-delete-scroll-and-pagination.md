# Upsert, Update, Delete, Scroll, and Pagination

## Why data management matters

A vector database is not a one-time upload destination. Real documents change. A user may edit a page, remove a file, change its permissions, or publish a newer version.

The database must stay consistent with the source of truth. This lesson covers the main lifecycle operations:

- Upsert: insert a new point or replace an existing point with the same ID.
- Update payload: change metadata without replacing the vector.
- Delete: remove points that are no longer needed.
- Scroll: read records in batches without performing a similarity search.
- Pagination: process large result sets gradually.

## 1. Use stable identifiers

I should assign a stable point ID or maintain a stable mapping from source documents to vector records.

For example, a source document may have the ID billing-guide-001 and be split into several chunks. The vector point IDs can be deterministic values derived from the document ID and chunk number.

A stable mapping helps an update job find and replace the correct chunks. Randomly creating new point IDs every time a document changes can leave stale chunks behind.

## 2. Upsert a point

~~~python
from qdrant_client import QdrantClient, models

client = QdrantClient(path="./qdrant_data")

client.upsert(
    collection_name="support_articles",
    points=[
        models.PointStruct(
            id=1001,
            vector=[0.12, 0.85, 0.20],
            payload={
                "tenant_id": "tenant-a",
                "document_id": "billing-guide-001",
                "title": "Download an invoice",
                "status": "published",
            },
        )
    ],
)
~~~

This is a learning example using a synthetic vector. Real vectors must be generated by the embedding model selected for the collection.

An upsert should be designed to be safe to retry. Repeating the same operation with the same stable ID and same content should not create duplicate logical records.

## 3. Update payload fields

Sometimes only metadata changes. For example, the article title may change or a document may move from draft to published.

~~~python
client.set_payload(
    collection_name="support_articles",
    payload={
        "title": "Download and view an invoice",
        "status": "published",
    },
    points=[1001],
)
~~~

This changes payload values for the selected point. It does not regenerate an embedding. If the underlying text content changes, the application should usually generate a new embedding and upsert the updated vector as well.

## 4. Delete a point

~~~python
client.delete(
    collection_name="support_articles",
    points_selector=models.PointIdsList(
        points=[1001]
    ),
)
~~~

A production delete workflow must consider more than the vector database. The source document, chunk records, caches, search indexes, and any derived copies may also need removal.

For legal or compliance requirements, define deletion propagation and retention policies explicitly.

## 5. Scroll through records

Similarity search answers “Which points are most similar to this vector?” Scroll answers “Give me records from this collection in batches.”

~~~python
records, next_offset = client.scroll(
    collection_name="support_articles",
    limit=100,
    with_payload=True,
    with_vectors=False,
)

for record in records:
    print(record.id, record.payload)

print("Next offset:", next_offset)
~~~

The offset is a continuation value returned by the database. I should pass it back for the next batch rather than assume that a page number is supported in the same way.

A simple loop:

~~~python
offset = None

while True:
    records, next_offset = client.scroll(
        collection_name="support_articles",
        limit=100,
        offset=offset,
        with_payload=True,
        with_vectors=False,
    )

    if not records:
        break

    for record in records:
        process_record(record)

    if next_offset is None:
        break

    offset = next_offset
~~~

The process_record function represents application logic that I implement for my use case.

## 6. Design document update workflows

Suppose a source document has ten chunks and is then edited to contain seven chunks.

A safe update process should:

1. Read the latest source version.
2. Split and normalise the updated text.
3. Generate compatible embeddings for the seven new chunks.
4. Upsert the new chunks using stable IDs.
5. Remove obsolete chunk IDs that belonged to the previous version.
6. Record the source version and processing status.
7. Verify that the search results contain the new content and not stale chunks.

This workflow should be idempotent: retrying it after a timeout should not create duplicate logical data or leave the document in an inconsistent state.

For large updates, use a temporary version or staged collection strategy if the application requires readers to see either the old complete version or the new complete version, never a partial mix.

## 7. Pagination and operational safety

Batch size affects memory, network use, and processing time. A batch of 100 may be reasonable for a small local exercise, but it is not a universal production setting.

For background jobs:

- Keep checkpoints so a worker can resume.
- Make each batch safe to retry.
- Apply rate limits to embedding provider calls.
- Track processed, failed, skipped, and deleted counts.
- Send repeated failures to a retry queue or dead-letter workflow.
- Avoid loading an entire large collection into application memory.

## Key takeaway

A production vector database needs a dependable data lifecycle. Stable IDs, idempotent jobs, pagination, and deletion propagation keep search results aligned with the real source documents.
